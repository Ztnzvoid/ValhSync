ValhSync

Cahier des charges du launcher qui synchronise les mods d'un serveur Valheim avec ses joueurs. Nom provisoire.

[Info : BepInEx] Loading [AzuCraftyBoxes 1.8.17] [Info : BepInEx] Loading [AzuExtendedPlayerInventory 2.4.13] [Warning:AzuCraftyBoxes] Peer (Steam_7656119xxxxxxxxxx) never sent version or couldn't due to previous disconnect, disconnecting [Warning:AzuExtendedPlayerInventory] Peer (Steam_7656119xxxxxxxxxx) never sent version or couldn't due to previous disconnect, disconnecting

Le joueur n'avait pas les bons mods, il a été éjecté, et il n'a vu qu'un message « Incompatible version ». ValhSync existe pour que ça n'arrive plus.

Décisions. Les choix marqués « par défaut » peuvent être discutés, mais pas changés sans l'accord de Ztnzvoid. Les points marqués à vérifier sont des hypothèses à confirmer par un test réel avant de s'appuyer dessus.

Profil de Ztnzvoid : administrateur systèmes et réseaux, 17 ans d'expérience, spécialisé infra de studios de jeu. Pas besoin de vulgariser les notions d'infra ; en revanche, explique les choix Rust qui ne sont pas évidents.

§1Le problème

Valheim n'a aucun système natif pour distribuer des mods. Iron Gate ne supporte pas officiellement le modding, et il n'y a pas de Steam Workshop, même en 1.0 (sortie le 9 septembre 2026). Tout passe par BepInEx et par des gestionnaires tiers.

Sur un serveur moddé, ça casse de plusieurs façons, toutes vécues en installant le serveur de Ztnzvoid :

  • Handshake de version. Beaucoup de mods (ceux basés sur ServerSync ou Jotunn) vérifient à la connexion que le client a le même mod, dans la même version. Si le client ne l'a pas, il est déconnecté, et le jeu n'affiche qu'un « Incompatible version » générique.
  • Mods incompatibles entre eux. Un reste d'EquipmentAndQuickSlots chez un joueur empêche AzuExtendedPlayerInventory de se charger (BepInEx refuse avec incompatible with: randyknapp.mods.equipmentandquickslots), et le joueur est rejeté par le serveur.
  • Sources éclatées. Depuis la 1.0, certains auteurs publient sur Hexium au lieu de Thunderstore. r2modman ne lit pas Hexium : un joueur qui passe par lui récupère parfois une version antérieure à la 1.0.
  • Distribution manuelle. Aujourd'hui, l'admin zippe BepInEx + winhttp.dll + doorstop_config.ini et l'envoie aux joueurs, à refaire à chaque mise à jour de mod.

ValhSync fait du serveur la source de vérité : le launcher du joueur compare son installation au manifeste signé du serveur, corrige les écarts, puis lance le jeu.

§2Périmètre v1

Dans la v1

  • valhsync-server : scanne le pack de mods de l'admin, produit un manifeste signé et sert les fichiers en HTTP.
  • valhsync : launcher joueur (interface graphique + mode CLI) qui rejoint un serveur via un code d'invitation, synchronise, puis lance Valheim.
  • Serveur : Windows (cas réel de Ztnzvoid : application Steam « Valheim Dedicated Server » lancée par .bat) et Linux.
  • Joueur : Windows en priorité. Linux et Steam Deck : détection et instructions affichées (voir §9).
  • Sauvegarde avant chaque synchro, retour arrière, mise en quarantaine des mods non gérés.

Pas dans la v1

Voir §14.

§3Principes non négociables

Aucune dépendance à un logiciel tiers. ValhSync ne dépend ni de Gale, ni de r2modman, ni de Jotunn, ni des API Thunderstore ou Hexium. Des crates Rust matures, oui ; un autre programme à installer, non.
Écrit de zéro. Pas de fork d'un outil existant. Ne jamais copier de code de Gale : il est sous GPL-3.0, et le copier imposerait cette licence à ValhSync. S'inspirer de son fonctionnement est permis.
Le launcher n'écrit qu'à l'intérieur du dossier du jeu, et uniquement dans les chemins autorisés (§8). Il n'exécute jamais un fichier téléchargé : il lance Valheim via Steam, point.
Solidité avant fonctionnalités. Chaque écriture disque est atomique et réversible. Un échec au milieu d'une synchro laisse l'installation dans son état précédent.
Messages d'erreur utiles. Chaque erreur dit ce qui s'est passé et quoi faire. Jamais de « Une erreur est survenue ».

§4Architecture

  Machine serveur                                    PC du joueur
 ┌──────────────────────────────┐                  ┌───────────────────────────────┐
 │ Valheim Dedicated Server     │                  │ valhsync (launcher)            │
 │  └ BepInEx/ (mods serveur)   │                  │  1. GET /manifest.json + .sig │
 │                              │   HTTP(S) TCP    │  2. vérifie la signature      │
 │ valhsync-server               │ ◀──────────────▶ │  3. compare aux hashs locaux  │
 │  ├ scanne pack + extras      │                  │  4. télécharge /files/<hash>  │
 │  ├ manifeste signé Ed25519   │                  │  5. applique (atomique)       │
 │  └ store adressé par hash    │                  │  6. lance Valheim via Steam   │
 └──────────────────────────────┘                  └───────────────────────────────┘
          ▲                                                   │
          └──────────── connexion jeu (UDP 2456-2457) ◀───────┘

Workspace Cargo proposé par défaut :

  • crates/valhsync-core : modèle du manifeste, scan, hash, signature, validation des chemins. Aucune I/O réseau. C'est ici que se concentrent les tests.
  • crates/valhsync-server : binaire serveur.
  • crates/valhsync : binaire joueur, CLI et interface graphique dans le même exécutable.

§5Le manifeste

Le serveur sert manifest.json et manifest.sig, une signature Ed25519 détachée calculée sur les octets exacts du JSON. Le client vérifie la signature avant de parser.

{
  "format": 1,
  "server_name": "Serveur de Ztnzvoid",
  "game_address": "valheim.example.org:2456",
  "generated_at": "2026-09-10T18:00:00Z",
  "pack_id": "b3:9f2c…",
  "managed_roots": ["BepInEx/core", "BepInEx/plugins", "BepInEx/patchers", "BepInEx/config"],
  "files": [
    { "path": "winhttp.dll", "size": 25088, "blake3": "…", "policy": "enforce" },
    { "path": "doorstop_config.ini", "size": 812, "blake3": "…", "policy": "enforce" },
    { "path": "BepInEx/plugins/AzuCraftyBoxes/AzuCraftyBoxes.dll", "size": 131072, "blake3": "…", "policy": "enforce" },
    { "path": "BepInEx/config/Azumatt.AzuCraftyBoxes.cfg", "size": 2048, "blake3": "…", "policy": "seed" }
  ]
}
ChampRôle
pathChemin relatif à la racine du jeu, séparateur /. Validé strictement des deux côtés (§8).
blake3Hash du contenu. Sert aussi de clé de téléchargement : GET /files/<blake3>.
policyenforce : toujours remplacé s'il diffère. seed : installé seulement s'il est absent, jamais écrasé ensuite (préférences du joueur : raccourcis, interface).
managed_rootsDossiers dont ValhSync a la responsabilité. Ce qui s'y trouve sans figurer au manifeste est un fichier « non géré » (§7).
pack_idHash de la liste triée des entrées. S'il n'a pas changé, le client n'a rien à faire.

§6Côté serveur : valhsync-server

Le point clé : le pack client n'est pas le dossier du serveur

C'est la leçon principale de l'installation du serveur de Ztnzvoid. Certains mods ne doivent tourner que sur le serveur (DiscordConnector), d'autres que chez les joueurs (EquipmentAndQuickSlots, BetterArchery, ConfigManager, Unshamed), et la plupart des deux côtés. Le pack distribué se construit donc ainsi : dossier BepInEx du serveur, moins les exclusions, plus un dossier d'extras réservés aux clients.

# valhsync-server.toml
[server]
name = "Serveur de Ztnzvoid"
bind = "0.0.0.0:2470"                          # port TCP par défaut, à ouvrir dans le pare-feu
game_address = "valheim.example.org:2456"      # adresse que le launcher donnera au jeu

[pack]
server_root = 'C:\Program Files (x86)\Steam\steamapps\common\Valheim dedicated server'
include = [
  "winhttp.dll", "doorstop_config.ini",
  "BepInEx/core/**", "BepInEx/plugins/**", "BepInEx/patchers/**", "BepInEx/config/**",
]
exclude = [
  "BepInEx/LogOutput.log", "BepInEx/cache/**",
  "BepInEx/plugins/DiscordConnector/**",       # serveur uniquement
]
client_extras = 'C:\valhsync\client-extras'     # même arborescence que la racine du jeu

[policy]
default = "enforce"
seed = ["BepInEx/config/**"]                   # les configs sont proposées, pas imposées
enforce = ["BepInEx/config/BepInEx.cfg"]       # sauf celles-ci

[limits]
max_file_mb = 200
max_pack_mb = 2048
max_files = 5000

Si le pack BepInEx contient d'autres éléments à la racine (par exemple un dossier unstripped_corlib), l'admin les ajoute à include. À vérifier sur le pack 5.4.2350 : lister précisément ce qu'il dépose à la racine, et adapter les valeurs par défaut de init.

Commandes

CommandeEffet
initCrée la config avec détection du dossier serveur, génère la paire de clés Ed25519 et affiche le code d'invitation.
scanConstruit le manifeste et affiche le résumé : nombre de fichiers, taille, différences avec le précédent.
serveSert le manifeste et les fichiers. Surveille les dossiers (crate notify) et reconstruit le manifeste après chaque modification, avec un délai de stabilisation.
inviteRéaffiche le code d'invitation.
rotate-keyNouvelle paire de clés et nouveau code d'invitation. Les joueurs devront réimporter le code.

API HTTP

  • GET /manifest.json et GET /manifest.sig
  • GET /files/<blake3> : le contenu, servi depuis un store adressé par hash. Aucun chemin de l'URL n'est jamais utilisé pour accéder au disque.
  • GET /health

Pas de listing, pas d'écriture, pas d'authentification en v1 : le contenu n'est pas secret, son intégrité est garantie par la signature. TLS optionnel (rustls) si l'admin fournit un certificat.

Code d'invitation

valhsync1: suivi de l'encodage base64url d'un JSON { "url": "http://hôte:2470", "pubkey": "…", "name": "…" }. Le joueur le colle dans le launcher ; la clé publique est épinglée à ce moment-là.

Exécution : console au premier plan en v1. Fournir un exemple d'unité systemd pour Linux et une note sur NSSM ou sc.exe pour Windows. Un vrai service Windows natif viendra plus tard.

§7Côté joueur : valhsync

Déroulé d'une synchro

  1. Localiser Valheim (§9). Refuser de continuer si valheim.exe tourne.
  2. Télécharger le manifeste et sa signature, vérifier avec la clé épinglée. En cas d'échec, arrêter et ne rien toucher.
  3. Calculer le plan : fichiers à ajouter, à remplacer, à retirer (anciens fichiers ValhSync qui ne sont plus au manifeste), et fichiers non gérés trouvés dans managed_roots.
  4. Première synchro, ou changement de clé : afficher le plan et demander confirmation. Ensuite, synchro automatique, avec le résumé affiché.
  5. Télécharger dans un dossier temporaire, vérifier chaque hash BLAKE3.
  6. Sauvegarder l'état actuel, appliquer en déplaçant les fichiers (renommages atomiques), enregistrer le nouvel état.
  7. Lancer Valheim.

Fichiers non gérés

Un fichier présent dans BepInEx/plugins sans figurer au manifeste peut casser la connexion (cas EquipmentAndQuickSlots). Par défaut, ValhSync le déplace dans BepInEx/_valhsync_quarantine/<date>/, hors du dossier scanné par BepInEx. Il ne supprime jamais un fichier qu'il n'a pas lui-même installé.

État local

  • %APPDATA%\valhsync\ (ou l'équivalent via la crate directories) : serveurs connus, clés épinglées, état du dernier pack appliqué (chemins et hashs installés par ValhSync).
  • %LOCALAPPDATA%\valhsync\backups\<date>\ : sauvegardes avant synchro. Garder les 5 dernières par défaut.

Interface

Une seule fenêtre, pensée pour des joueurs qui ne veulent pas réfléchir :

  • Liste des serveurs, avec un bouton « Ajouter un serveur » qui demande le code d'invitation.
  • Pour le serveur sélectionné : un statut (« À jour », « 3 mods à mettre à jour », « Serveur injoignable »), puis un bouton « Jouer » qui synchronise et lance le jeu.
  • Menu secondaire : « Revenir à la version précédente », « Voir la quarantaine », « Jouer sans mods ».
  • « Jouer sans mods » renomme winhttp.dll en winhttp.dll.off (BepInEx ne se charge plus) puis lance le jeu. La synchro suivante le rétablit.

Un seul pack actif à la fois, puisqu'il n'y a qu'une installation du jeu. Passer d'un serveur à l'autre resynchronise.

Mode CLI

valhsync join <code>, valhsync sync [serveur], valhsync play [serveur], valhsync status, valhsync rollback, valhsync vanilla on|off. Le CLI arrive avant l'interface graphique (§11) : il sert de base aux tests.

§8Sécurité

Point de départ honnête : un plugin BepInEx est du code .NET arbitraire, qui tourne avec les droits du joueur. Rejoindre un serveur ValhSync revient à faire confiance à son admin, exactement comme quand on accepte son zip de mods. ValhSync ne peut pas protéger contre un admin malveillant ; il doit en revanche empêcher tout le reste, et limiter les dégâts.

MenaceParade
Interception ou modification en transitManifeste signé Ed25519, clé épinglée via le code d'invitation. Chaque fichier vérifié par son hash BLAKE3 avant installation.
Clé du serveur qui changeRefus, avec un avertissement explicite. Le joueur doit réimporter un code d'invitation obtenu directement auprès de l'admin.
Chemin piégé dans le manifeste (../, chemin absolu, lettre de lecteur, UNC, composant vide, noms réservés Windows comme CON ou NUL)Rejet du manifeste entier. Seuls sont acceptés winhttp.dll, doorstop_config.ini, BepInEx/**, et les entrées racine explicitement autorisées par la config client.
Lien symbolique ou jonction dans le dossier du jeuNe jamais suivre de lien. Vérifier que le chemin canonique final reste sous la racine du jeu.
Serveur qui envoie des fichiers énormesLimites de taille par fichier et par pack, nombre de fichiers maximum, délais d'expiration. Téléchargement arrêté dès que la taille annoncée est dépassée.
Exécution de code par le launcherAucune. Le launcher ne lance que Valheim, via Steam.
Côté serveur : accès disque via l'URLStore adressé par hash uniquement, pas de listing. Tourne sous un utilisateur dédié sans privilèges.
Chaîne d'approvisionnement RustCargo.lock versionné, cargo deny et cargo audit en CI, dépendances limitées au nécessaire.

La validation des chemins vit dans valhsync-core, avec une batterie de tests de chemins malveillants. C'est la fonction la plus critique du projet.

§9Valheim et BepInEx : ce qu'il faut savoir

  • Chargement de BepInEx. Sous Windows, le winhttp.dll (Doorstop) placé à côté de l'exécutable injecte BepInEx au lancement. C'est vrai pour valheim.exe comme pour valheim_server.exe. Pack de référence : BepInExPack_Valheim 5.4.2350, publié pour la 1.0.
  • Découverte des plugins. BepInEx cherche les DLL récursivement dans BepInEx/plugins : un sous-dossier par mod est une convention, pas une obligation. Les patchers vont dans BepInEx/patchers, pas dans plugins.
  • Vérifier le chargement. Dans BepInEx/LogOutput.log, chaque mod chargé produit une ligne Loading [Nom Version]. Le launcher peut s'en servir après un lancement pour signaler les erreurs de chargement (amélioration possible).
  • Localiser Steam et le jeu. Windows : clé de registre HKCU\Software\Valve\Steam\SteamPath. Linux : ~/.steam/steam, ~/.local/share/Steam, ou Flatpak ~/.var/app/com.valvesoftware.Steam/.local/share/Steam. Lire ensuite steamapps/libraryfolders.vdf, puis appmanifest_892970.acf pour le champ installdir. Toujours permettre un chemin manuel.
  • Identifiants Steam. Valheim : 892970. Valheim Dedicated Server : 896660.
  • Lancer le jeu. Via l'URL steam://run/892970//+connect%20hôte:port/. À vérifier : le format exact de l'URL, et la prise en charge de +connect et +password par Valheim 1.0. Si +password n'existe pas, le joueur tapera le mot de passe en jeu.
  • Linux et Steam Deck. Avec Proton, BepInEx ne se charge que si l'option de lancement Steam contient WINEDLLOVERRIDES="winhttp=n,b" %command%. Le client Linux natif, lui, passe par start_game_bepinex.sh. En v1, le launcher détecte le cas et affiche l'instruction ; il ne modifie pas la config de Steam.
  • Consoles. La 1.0 ajoute le crossplay PS5 et Switch 2, mais les consoles n'ont aucun support des mods. Un serveur qui impose des mods exclut de fait les joueurs console : à dire clairement dans la documentation admin.
  • Succès. En 1.0, n'importe quel mod BepInEx bloque les succès. Le mod client Unshamed (Azumatt) lève ce blocage : un bon candidat pour les extras clients, mais c'est le choix de l'admin.
  • Version du jeu. Un « Incompatible version » peut aussi venir d'un décalage de version du jeu entre serveur et client, après un hotfix appliqué d'un seul côté. Amélioration possible : lire la version du serveur dans son log et prévenir le joueur. À vérifier : le format de la ligne de version dans le log.
  • Licences des mods. Redistribuer les DLL depuis le serveur est courant entre amis, mais certains auteurs l'interdisent. La documentation admin doit le rappeler. Une version ultérieure pourra référencer l'URL officielle du fichier au lieu de l'héberger.

§13Questions ouvertes, à poser à Ztnzvoid avant M0

  1. Nom. On garde ValhSync ?
  2. Licence. Par défaut, MIT OR Apache-2.0, la convention de l'écosystème Rust. Autre préférence ?
  3. Interface. egui par défaut (exécutable unique, pur Rust). Tauri serait plus joli mais dépend de WebView2 sous Windows. Choix ?
  4. Serveur Linux. Le serveur actuel tourne sous Windows. Le support Linux côté serveur fait-il partie de la v1, ou peut-il attendre ?
  5. Port. 2470/TCP par défaut, ça convient ?
  6. Hébergement des DLL. En v1, le serveur héberge lui-même les fichiers (usage privé). OK, ou faut-il prévoir dès maintenant le mode « URL officielle » ?

§14Hors périmètre v1

  • Télécharger des mods depuis Thunderstore ou Hexium, ou parcourir un catalogue.
  • Mise à jour automatique du launcher lui-même.
  • Patchs différentiels ou compression des transferts.
  • Plusieurs packs installés en parallèle.
  • Modifier automatiquement les options de lancement Steam (cas Linux et Proton).
  • Service Windows natif pour valhsync-server.
  • Toute plateforme console.
